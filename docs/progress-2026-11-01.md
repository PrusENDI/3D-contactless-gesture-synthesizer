## 修复：LIVE 琶音每 tick 打包 4 个事件（`00f3476`）

用户定位到流水线错位：`PIPELINE_NOTE=1` 时 `candidate_*` 是组合信号，打包用寄存一拍的
`emit_candidate_*`，而状态推进又发生在打包那一拍 —— 同一步骤被选中两拍，每个 tick 打包
`OFF, OFF, ON, ON` 四个事件（实测 32 事件/s，应为 16）。

修复：状态推进移到**候选进流水线的同一拍**，用组合 `candidate_type`；
`PIPELINE_NOTE=0` 仍走原来的打包时推进。

同轮附带两处：

1. `arp_state / arp_pair / arp_note` 从未复位（仿真里是 X，板上靠上电寄存器为 0）；
   已加进复位分支。
2. `bpm_auto` 由 `x*120 >> 17`（满量程 30+60=90 BPM）改为 `x*30 >> 16`（30..59 BPM）。

测试：`tb/tb_live_arp_rate.sv`，9 个 tick 期望 ON=9 / OFF=8；修复前 **18/16**，修复后 **9/8**。

注意：LIVE 的 BPM 由 X 轴决定（30..59），**BPM=120 在 LIVE 到不了**；"10 s 160 事件"
只在固定 BPM=120 时成立（8 tick/s × 2 × 10 s），而 LIVE 会用 `bpm_auto` 覆盖 CSR。
板上按 X 位置算：`events/10s ≈ 2 × 10 × (30 + floor(x*30/65536)) / 15`。

## 修复：X→BPM 只在 UART 命令到来时才算（`6f37684`）

根因：`bpm_auto_d <= cursor_frame_done && (bpm_auto != bpm_auto_q)` 这一段写在
`if (cmd_valid && cmd_ready)` **里面**。`cursor_frame_done` 是单拍脉冲，UART 命令与它同拍
的概率几乎为 0，所以 `bpm_auto_q` 自复位后就没更新过，LIVE 一直用 120 BPM。

修复：把映射抽成 `rtl/v2_live_tempo.sv`，在顶层无条件实例化：

```verilog
v2_live_tempo u_live_tempo (.clk(clk_sys_100m), .rst_n(rst_sys_n),
    .frame_done(cursor_frame_done), .x(cursor_x[15:0]),
    .bpm(bpm_auto_q), .bpm_we(bpm_auto_we));
```

测试 `tb/tb_live_tempo.sv`：复位 120 → x=0 得 30（一次写脉冲）→ 同一目标不重复写 →
x=65535 得 59（再一次写脉冲）。`gate` 0/0、`sim.py` PASS。

## 修复：进 LIVE 时分频器没有重新装载（`707c0bd`）

上板复测仍然是 8 tick/s（120 BPM），与仿真不一致。原因：tempo 映射在**所有模式**下都跑，
它那唯一一次写脉冲发生在 IDLE——而 `bpm_we` 在 IDLE 被 `mode_live ? bpm_auto_we : bpm_we_q`
挡住，脉冲丢了。之后进 LIVE 时 `bpm_auto_q` 已经是 30..59，但目标不变、不再产生脉冲，
分频器就一直用复位值 6000（120 BPM）。

修复：加 `mode_live` 上升沿，进入 LIVE 时强制写一次分频器：

```verilog
wire bpm_sel_we = (mode_live ? bpm_auto_we : bpm_we_q) || (mode_live && !mode_live_q);
```

测试 `tb/tb_live_tempo_top.sv`（顶层 + 输入探针，让游标帧真的在跑）：
先确认 IDLE 下 `spt_q` 仍是 6000，再 force `mode_reg=LIVE`，要求 `spt_q ≈ 720000/bpm_auto_q`。
**去掉这一项会红**（`spt=6000 bpm=45`），加回即绿。

## 修复：LIVE 自动 tempo 不再清零相位；无手不再出音（`79b2027`）

上板听感“节奏完全乱、声音不跟手”，根因有两个：

1. `v2_tick_gen` 每次 `bpm_we` 都 `tick<=0; phase_cnt<=0`。自动 tempo 在 LIVE 里每帧都可能写
   一次，手一动相位就被不断清零，tick 永远攒不满一个周期。
   修复：`v2_tick_gen` 增加 `restart` 输入；宿主写 BPM（非 LIVE）才清零，LIVE 自动 tempo
   只重算 `samples_per_tick`。顶层 `.restart(!mode_live)`。
2. arp 的 tick 分支不检查门控，手离开后仍每 tick 起一个 `map_note(旧 y)` 的音。
   修复：tick 分支要求 `gate_now`；落手时只发一次释放 OFF，之后的 tick 静音。
   同时给释放分支加 `!candidate_valid_q`，避免 OFF 进流水线后、`active` 还没清零时重复释放。

测试：
- `tb_tick_gen` 新增 keep-phase 用例（`restart=0` 时 tick=2 不被清零，`restart=1` 才清零）；
- `tb_live_arp_rate` 新增“落手”用例：9 tick 后拉低 gate 并送一帧，期望 ON=9 / OFF=9，
  再 3 个 tick 不再产生事件（第一次实现多出一个 OFF，被这个用例抓住）。

## 说明：规则引擎的 `tick` 端口接的是 `sample_index`（2026-11-01）

`v2_live_rule_engine.tick` 在顶层接的是 `sample_index`（48 kHz 采样计数），**不是音乐 tick**：

```verilog
.touch(cursor_engaged), .bow(cursor_engaged), .tick(sample_index),   // top:308
```

因此追踪模式里的 `candidate_due = (rule_tick - last_event_tick) >= MIN_EVENT_TICKS`
是 **4 个采样（83 µs）** 的节流，和 BPM 无关；追踪模式的换音只由帧（138 Hz）驱动。
只有 arp 走音乐 tick（`mtick`）。曾把这条误判成“4 个音乐 tick”，据此得出“低 BPM 下换音要等
1–2 s”的错误结论，记录在此以免重犯。

如果以后把 `.tick()` 改成音乐 tick，`MIN_EVENT_TICKS` 才会变成随 BPM 变化的节流，
那时需要换成时间基准。

## 修复：追踪模式整条事件路径是死的（`4ca61bb`）

用户报“追踪模式 Y 不控制音高”。上板表现：`gate=1`、`y` 在变、`active=0`、事件计数不动，
即使完成左边缘起弓也没有 `NOTE_ON`。

根因两个，都在 `v2_live_rule_engine.sv`：

1. **打包条件被 `arp_mode` 挡住**：

   ```verilog
   if (arp_mode && emit_candidate_valid && ...) begin   // 旧
   ```

   追踪模式产生的候选**永远不会打包成事件**，所以 `active`/`active_note` 永远不更新。
   修复：去掉 `arp_mode &&`，打包在两种模式下都执行；只有 arp 的状态推进保留 `arp_mode` 守卫。
2. **追踪分支被 `!bad_frame` 挡住**：`bad_frame` 含 `degraded`，而当前传感器约 78% 的帧被判
   降级，于是换音/起音全被关掉。修复：追踪分支只要求 `!rule_frame_gap`（真丢帧才挡），
   `degraded` 视为“精度下降但 y 可用”。

测试 `tb/tb_live_track_pitch.sv`：`frame_degraded=1` 的帧流下，左边缘起弓后应出 note=60
（y=20000），再把 y 移到 45000 应变成 67。修复前 `active=0`（红），修复后两条都过（绿）。

注意：这个 tb 必须让 `tick` 每拍递增（顶层接的是 `sample_index`），否则 `candidate_due`
会在首个事件后永远为假。

## LOOP 多轨：Task 3 两轨断言 + Task 4 板上验收（2026-11-01 16:4x）

### 两轨必须“逐轨提交、逐轨发布”（计划里的顺序不可达）

计划 Task 3 原来写的是“两次 `0x28` 再 `MODE=PLAY`”。这个顺序在 RTL 上做不到：

- `COMMIT_REQUEST` 之后 store 的 `busy = copy_active || commit_pending`，而
  `ctrl_ready = !busy`，所以第二次 `PREPARE_RECORD` 会被拒绝；
- `loop_ctrl_pending` 因此挂住，`cmd_ready`（要求 `!loop_ctrl_pending`）会挡住所有后续
  命令，UART 直接不再受理——表现出来就是“脚本卡在第二次 `0x18` 没有响应”。

可达且语义正确的顺序是**提交一轨 → `MODE=PLAY` 跑到边界发布 → 下一轨**。
`PREPARE_RECORD` 的 active→shadow 复制正好把已经发布的轨带进新的 shadow bank，
所以逐轨发布不会丢掉前面的轨。板上 page1 的 `rec` 字段直接证明了这一点（见下）。

### `tb_stage2_loop_e2e` 的两轨用例（`bc76824`）

1. STOP 掉上一跑挂起的提交（`0x14=1`），确认 `commit_pending` / `busy` 释放；
2. 轨 0：`0x0C=0` → `0x18` → 32 拍斜坡 → `0x28`；读 shadow 计数：轨 0=7、轨 1=0；
3. `MODE=PLAY` 一圈到边界发布（`loop_active_valid=1`、`commit_pending=0`）；
4. 轨 1：`0x0C=1` → `0x18` → 32 拍恒定高音 → `0x28`，**并在提交进行中写 `0x0C=0`**；
   读 shadow 计数：轨 1=1、轨 0 仍=7（说明锁存生效、且轨 0 没被覆盖）；
5. `MODE=PLAY`：第一圈到边界发布，第二圈测量 —— 轨 0 出 note 57、轨 1 出 note 72，
   两条 `NOTE_ON` 相隔 790 ns（同一遍扫描、同一 tick 0），`steals=0`；
6. STOP 后 `active_voice_count=0`、`commit_pending=0`。

计数必须在**提交后、`MODE=PLAY` 之前**读：边界翻 bank 时会清掉退役 bank 的计数
（store 的 `counts[active_bank][t] <= 0`），PLAY 之后再读 `loop_record_count` 只会看到 0。
这正是 `717f12c` 提交信息里记的“第一次写这个用例读到 0”的原因。

红/绿：把 `rtl/mgc3130_v2_top.sv` 临时退回 `HEAD~1`（未锁存 track）跑同一个 tb →
`Fatal: take 2 stored 0 events in track 1, expected 1`；恢复后 `UNIT tb_stage2_loop_e2e: PASS`。

关于 `max_voices=8`：本 tb 把一拍压到 2600 个 50 MHz 周期（≈1.5 个音频采样），
而声部释放尾巴是 64 个采样，所以**单一轨自己的音也会叠**。因此“两轨同时发声”的证据
不是这个数字，而是“同一遍扫描、同一 tick 0 送出两个不同音高的 `NOTE_ON` + `steals=0`”。
真实时间下（板上）这个数就是 2。

## 修复：PLAY 回放听不见（是电平，不是静音）

### 1. 包络终于乘到音频上了（`5337ac0`）

改动全在 `rtl/v2_voice_engine_banked.sv`，两级寄存乘法，不动 CSR 与契约：

```systemverilog
calc_env_gain <= envelope_gain(rd_envelope, rd_gain);          // 24 位乘积取 [23:8]
wire signed [47:0] calc_osc_vca =
    ($signed(calc_osc_sum[31:0]) * $signed({1'b0, calc_env_gain})) >>> 16;
mix_acc <= mix_acc + calc_osc_vca;                              // 累加级两处都换成它
```

于是 `mixed_sample = saturate(Σ_slot (osc_sum × (env × velocity >> 8) >> 16))`。
锯齿路径与波表路径共用同一个 `calc_osc_vca`，DSP 6→8。

**踩到的坑（红测抓出来的）**：直接写 `calc_env_gain <= (rd_envelope * rd_gain) >>> 8;`
时 Verilog 按**目标宽度**给乘法定尺寸，24 位乘积被截成 16 位（`49152×255` 变成 `61440`），
稳态只剩 1 LSB。改成内部 24 位变量的函数才正确。这类错误"有声部、有声音"根本发现不了。

`tb_voice_vca`（新）：起音首采样恒为 0、起音是斜坡、稳态 `(osc_sum × (env×gain>>8)) >> 16`、
力度 0 完全静音、192:255 的幅度比（±1 LSB）。实测 **vel 255 → 1528、192 → 1150、128 → 383**，
与手算一致。既有 `tb_voice_wt_source` / `tb_wt_voice_poly` / `tb_top_wt_voice` 的绝对电平原按
新物理重算（46 / −47、12238、71），**不是放宽**。

### 2. 每个声部两个振荡器不再同相（`97da308`）

激活字（`pending_activate` 唯一写者，见下一条）：

```
phase_a = 0                     phase_b = 0x8000_0000      // 错开半周期
step_a  = base                  step_b  = base - (base >> (11 - velocity[7:6]))
target_a= base                  target_b= step_b           // 目标带同样偏移
```

四档 = 0.05% / 0.10% / 0.20% / 0.39%（纯移位，不用 DSP）。`target_b` 必须一起偏，
否则 `bounded_step` 会以 ≤512/采样把失谐拉回基准、约 300 采样后消失。
`tb_voice_detune`（新）检查两条激活路径的每个字段 + slot 0 的首次写回
（`phase_b = 0x80000000 + base - det`），证明预置真的进了累加器、两个累加器从第一采样起就不同速。

### 3. 时序：失谐差点把 80 MHz 打穿（`0218fa6`）

第一次构建（`impl/v2_board_top_vca_detune`）CLS 10693、**Fmax 54.149 MHz、worst −5.968 ns、
TNS −3777.7 ns、setup 违约 1631**（基线 69.73 / −1.841 / −916.9 / 1163）。`.tr` 里 25 条最差路径
全是同一个锥：启动点是事件数据 mux（`mode_reg_1` / `u_loop_sched/event_valid`），穿音符 ROM（约 6 ns）、
`apply_delta`、`detuned_step`，终点是状态 bank 的写数据脚 `state_bank/g_lane[11]`
（= `bank_wr_data[191:160]` = `target_b`），到达时间 21.309 ns 对 12.5 ns 周期。

根因：激活原来在**接受事件的同一个周期**写 bank，写数据只能来自事件总线。

修法：所有 NOTE_ON 都先落到已有的单条邮箱，由 `pending_activate` 在下一拍写 bank——
即"激活也走抢声部那条路"。于是 ROM→触发器（不再是 ROM→BSRAM），bank 写数据全部来自寄存器，
顺带删掉了直接分支里重复的一份失谐逻辑。行为只是晚一拍；如果扫描恰好在激活那拍开始，
该声部 `rd_active` 仍为 0 会被跳过，不会读到旧字。

### 3. 三个根因（都已写回设计文档）

1. **乘法操作数超 DSP 片宽**：Gowin DSP 是 27×18，而 LFO 里三处 `{16'd0,x}*{16'd0,y}` 是 32×32、
   滤波器里 `*960`/`*271` 用了真乘法（操作数 34/36 位）→ 综合器退回 LUT 乘法阵列，
   凭空多 8460 个逻辑单元。改成 16×16 + 移位加后降到 21317（过线）。
2. **DSP 片只有 28 个，27 位数据通路每个乘法要 2 片**：设计文档 §11.4 估"7~8 个 DSP"，
   实测滤波器一个就要 13 个（27×18 单片）且总需求 30 片 > 28 片。**"并行乘法器"这个前提
   在这个器件上错了**——正确做法是一个 DSP 时分复用 14 拍（每采样 1667 拍预算）。
3. **组合链跨模块**：LFO 的 `offset_ci` 原本是组合输出，直穿到滤波器系数表地址，形成 ~50 ns 路径；
   LFO 内部 3 个正弦乘法也要串起来。改成"输出寄存 + 正弦每拍一级流水"后 Fmax 20 → 46 MHz。

### 4. 还差一步（等用户决策，未做）

最差 −9.20 ns 完全在顶层，与滤波器/LFO 无关：
`u_wt_playback → wt_quiet 移位加 → mult_3201（LIVE 包络乘法，仍是 LUT 阵列）→ 音频 mux →
音量乘法（2 片 MULT27X36）→ 饱和 → I2S`。

### 3. 音频链存活（`scripts/board_filter_demo.ps1 -SkipUpload -HoldMs 6000`）

- **exit 0**。脚本每个写都做写后读回、不等即 throw，四组全部相等：
  `0x40 = 0x01000120`（wrote 同值）、`0x40 = 0x01000090`、`0x44 = 0x01800500`、

- 用了 `-SkipUpload`，而板子刚烧完、shadow 是空的，所以本项只证明
  `0x40/0x44/0x90` 的写读路径与音频链的寄存器面仍在；**没有听任何东西，也不判断声音**。

### 4. 三个 P2b 寄存器（板上实测）

- 复位值：`0x94 = 0x01001000`、`0x98 = 0x0400C000`、`0x9C = 0x02000000`
  （与 `tb_top_p2_csr` 逐位一致）。
- 写 `0x94 = 0x01000080`（attack 128）→ ACK（`type=0x80, err=0x00`），读回 **`0x01000080`**。

### 5. 退役 CSR 的实测回包

- 写 `0x48 = 0` → **NACK `0x81`，`err=0x02` = `BAD_ADDRESS`**。
- 读 `0x48` → 同样 **NACK `0x02`**。
- 结论：链路在地址门（`v2_address_valid` 不再覆盖 0x48–0x5C）就拒绝，走不到数据门，
  所以不可能是 `BAD_DATA(0x07)`；`HANDOFF.md` / `host-tools-and-gui-controls.md` 原来写的
  `BAD_ADDRESS (0x02)` 与实测一致，本轮无需改错误码。

### 两次空录制的排查（记下来，别再误判）

前两次录制 `contour has 0/32 non-zero samples`，我一度怀疑 `capture_full` 卡住。查代码后否掉：
`v2_loop_contour_capture.sv` 的 `arm` 分支会清 `full`（第 47 行），第二次日志也证明它被重新武装。
真正原因是**录制窗口里手不在场**——采集逻辑是 `mem[wr] <= y[15:6]` 且 `valid_mask[wr] <= engaged`，
所以"全 0"等于"每个 tick 那一刻 `cursor_y` 近 0 或未 engaged"。

## 2026-11-02 晚上：四轨录制（成功）+ 两个脚本前提的坑

`board_stage2_loop.ps1 -Tracks 4` 在 P2b 位流上成功：

```
STAGE2 LOOP RESULT: PASS (track 0=1 note(s), track 1=5 note(s), track 2=3 note(s), track 3=5 note(s);
                          max_voices=4, steals=0, silent after STOP)
```

4 轨共 14 个音符，播放时 `active_voices` 峰值 **4**（`steals=0`），`STATUS=0x304`（mode=PLAY、loop_active=1）。

### 坑一：清场步骤只有「本来就没发布过」才能过

`board_stage2_loop.ps1` 的开头写 `STOP → CLEAR_ALL → MODE=PLAY`，然后等 `STATUS[8] loop_active_valid == 0`
出现，以此判定「空 bank 已发布」。实测：只要板上**已经发布过一轨**，这个条件在 15 秒内永远不成立
（`CLEAR_ALL` 只清 shadow，不把 `loop_active_valid` 归零），脚本报
`FATAL: the empty bank was never published (no loop boundary?)` 并以 14 退出。
之前每次「清场成功」其实都是因为板上本来就是空的（`STATUS=0x200`，bit8 已是 0）。

**当前的绕法**：重烧位流（SRAM 配置，烧完 loop 状态全清），再上传波表、再录。
**正确的修法（未做）**：清场后补一次真正的发布请求（`0x28 COMMIT`，或 RTL 侧让 CLEAR_ALL 显式置
`commit_pending`），这样局部失败的一轮可以恢复，不必每次重烧。

### 坑二：多轨之间没有准备时间

第一次录 4 轨时 track 0 成功（4 音符）、track 1 立刻空了——它的录制窗口在 track 0 发布后 4 秒就打开。
给脚本加了 `-PrepareSeconds N`（每轨武装前倒计时，默认 0 保持旧行为）。用 `-PrepareSeconds 8` 重跑，
4 轨一次过，track 2/3 的轮廓都是 **32/32 非零**。

### 教训

「没有数据」的录制类失败，先分清是**采集条件**（手不在场、`engaged=0`）还是**状态机前提**
（`loop_active_valid`、`capture_full`）。这次两种失败各出现一次，症状都是「0/32 非零」，但原因完全不同。
