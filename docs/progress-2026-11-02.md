## 台架（2026-11-02 晚，板子在 IDLE，`0xB0=0x5A5A0003`）

### 1. 写路径节拍：**突发不可用**，保持逐条

`scripts/gui_burst_bench.py` 三档节拍全部 0 接受。深挖后是两个独立问题：

- **seq 是 8 位**：1024 条的突发里 seq 每 256 条回绕，按 seq 配对必然崩。→ `burst` 现在拒绝 >255 条。
- **板子会丢命令**：60/200/1000/2000 µs 间隔都只回约 36/64（56%），裸 pyserial 复现同样结果，
  所以不是适配层；也不再复现 2026-11-01 那次"400/400 全收"（那次是读 `0xB0`，板子状态不同）。

**决定**：突发关闭，上传与读回逐条等 ACK。实测（每次命令 17.2–17.6 ms）：

| 操作 | 命令数 | 墙钟 |
| --- | --- | --- |
| 九参数预设应用（写 + 读回） | 18 | ≈0.3 s |
| 1024 点上传 | 1029 | **18.1 s** |
| 1024 点逐点读回 | 2048 | **35.3 s** |

### 2. 台架抓出两个真 bug（都已修、都有测试）

- **`SerialPort.read` 每次改 `port.timeout`** → pyserial 的 setter 会重配端口，Windows 下
  **清掉驱动缓冲区** → 应答帧头被吃掉（实测收到 18/21 字节的残帧）。改成开端口时设一次
  timeout=0，读时轮询 `in_waiting`。
- **`read_table` 连读 1024 次拿到的是同一个点**：`WT_DATA` 读**不自增**索引（只有写入自增，
  `mgc3130_v2_top.sv:1478`），`board_readback.ps1` 是每点先写 `0x64`。改后实测 **1024/1024 全等**。

## 17.6 ms 的来源：查清了，是驱动，且是历史遗留

用户问"为什么上传这么久、是不是历史问题"。查证结果：

| 证据 | 结论 |
| --- | --- |
| `UART_BAUD = 1_000_000` 自初始提交 `cafb93d` 起未变 | 波特率不是变量 |
| `artifacts/board/wt_upload.log`：`19:07:03.837` 开写 → `19:07:22.161` 拿到 `WT_STATUS` | **2026-10-31 第一次成功上传就是 18.32 s / 1027 条 = 17.8 ms/条** |
| 今天控制台实测 | 18.1 s（17.6 ms/条）——**没有回归** |
| `docs/` 全文搜索 `latency\|延时\|FTDI\|定时器` | 一条都没有：**从来没人查过** |
| COM4 设备 | FTDI **FT2232**（`VID_0403+PID_6010`，就是高云烧录线）；一条命令纯线上时间 0.33 ms |

顺带解释了 `progress-2026-10-31.md:147` 记的"回包滞后一条命令、`err=5 SEQUENCE`、读回全 0"——
那是 16 ms 定时器造成的**迟到回复**，当时被当成协议问题绕过去了。

**尝试改（失败，已还原）**：`HKLM\...\FTDIBUS\VID_0403+PID_6010+2025030317B\0000\Device Parameters\LatencyTimer`
16 → 1，重启设备后复测仍是 **16.00 ms**（20/20 帧有效）。这类 VCP 驱动的实际延时在设备 EEPROM /
Device Manager "高级"对话框下发的 IOCTL 里，注册表这一项不生效。已还原成 16，机器上不留改动。
**结论：接受现状**——上传 18.1 s、读回 35.3 s；三帧上传按"只传改动过的帧 + 逐帧进度条"做。

## LIVE 步进琶音的敲击声（2026-11-02 晚）

用户报的"step arpeggio 每一步一声敲击"不是相位问题，是**包络问题**，而且只在 arp 模式下。

### 先量再改

新增 `tb/tb_live_arp_step.sv`：真 UART 上传正弦表（幅度 0x3000），手在 cursor 滤波器的输出边界注入
（`cursor_x/y/z`、`cursor_state`、`cursor_frame_done` 强制，tick 由台架打），每个 `sample_ce` 记一次
`dut.i2s_sample`，同一只手、同一个音（y=3000 → note 55 / G3）：

| 量 | 修前 | 修后 |
| --- | --- | --- |
| arp **开**：每个 NOTE_ON 前后 ±12 样点的最大 \|sample[n]−sample[n−1]\| | **726** | **23** |
| arp **关**：稳段 600 样点的最大 \|sample[n]−sample[n−1]\| | **28** | **28** |
| arp 关 600 样点 dump 的 SHA256 | `B2F55FE072626DF4875D4E5FE8A07E18354BD147F37C11B4BE4677A81DBFF544` | 同左，逐字节相同 |

台架断言 `STEP_LIMIT = 80`：正弦本身约 28，包络跳变约 726，修前必红、修后过。

### 机制（不是相位）

修前边界 8 个样点（`wt_env` 与 `u_wt_playback.phase` 同时记，`idx` 是相位高 10 位）：

```
n=1299 sample=-486 env=45872 idx=616 phase=0x9a28d750
n=1300 sample=-503 env=0     idx=620 phase=0x9b347114   <- 包络在 1 个 sample_ce 内 45872 -> 0
n=1301 sample=-520 env=96    idx=625 phase=0x9c400ad8
n=1302 sample=0    env=192   idx=629 phase=0x9d4ba49c   <- 输出晚 2 个 sample_ce 才塌到 0
```

- 相位每拍固定 +`0x010B_99C4`（G3 的 increment），**跨边界完全连续**：`u_wt_playback` 的 phase 只被
  `rst_n` 复位，NOTE_OFF/NOTE_ON 都不动它。原假设"相位在事件上复位、与包络错开一个样点"**不成立**。
- 真正的跳变是 `wt_env`：`hit_sticky` 让它在一个 `sample_ce` 内从 45872 掉到 0，再按 `ENV_ATT=96`
  重新起音（≈10 ms）——满幅到 0 的一步 + 10 ms 渐入，就是那声敲击。
- `dut.u_voice` 确实在每次 activation 把 `bank_wr_data[31:0]` 写成 0（本轮 LIVE 里 4 次，台架打印
  `last bank phase write 0x00000000`），但 LIVE 的 I2S 走 `u_wt_playback → 0.1016 trim → wt_env →
  i2s_sample_raw`，`u_voice` 的输出在 LIVE 根本没进 mux，所以那个相位复位与可听声音无关。
- 输出相对 `wt_env` 晚 2 个 `sample_ce`（`wt_live_q` 一级、`i2s_sample_raw` 一级）。

### 修法

`rtl/mgc3130_v2_top.sv`：加 `live_env_hit = live_note_hit && !thresholds_reg[23]`，`hit_sticky` 只在
`live_env_hit` 上置位。即 **arp 模式下琶音步进不再清零包络**；包络只在手（gate）进出时动，
同音高重复步进是连续音，换音高是 legato（相位连续、幅度不变）。非 arp 的 frame-level tracking
仍走"每个 NOTE_ON 复位"，一行没改。

- 只多一个 AND 项（`thresholds_reg[23]` 本来就在寄存器里）：预计 **+1~2 LUT**，0 寄存器、0 DSP、0 BSRAM。
- PLAY 不受影响：`wt_env`/`wt_live_q` 只在 `mode_live` 时进 `i2s_sample_raw` 的 mux；PLAY 用
  `wt_trim_q`/`fx_quiet`，不经过 `wt_env`。
- 舍弃的备选：**只在音高变化时清零**（HANDOFF §6 的原提案）。换音高那一下仍是 45875→0 的一步，
  只是次数变少；本轮按"去跳变"做，换音高听感是 legato。若以后要重音，正确做法是给包络加限速斜率。

## LOOP 卡顿：34 秒死链

**现象**：用户报"loop 模式特别卡"。日志（`session-20261102-220501.jsonl`，4831 条）显示两件事：

1. **空转 14 条命令/秒**：`refresh()` 每 0.5 s 发 `0xE8/0x34/0xF8/0xE0` + `0x00` + `0x08` + `0x7C`，
   全在 Tk 线程上，25% 的界面时间在等串口。
2. **22:07:37 → 22:08:11 正好 34 秒**、28 条 `no usable reply`，期间每秒 1.3 s 的空档就是三次超时。

**根因**：`BOUNDARY_TIMEOUT_CYCLES = 32'd3_400_000_000`（`mgc3130_v2_top.sv:16`，100 MHz → 34.0 s）。
用户的操作序列是 `arm(0) → arm(1) → commit → arm(2)`：提交后 `commit_pending` 一直等小节边界，
store 的 `busy` 又挡住 `ctrl_ready`，顶层于是把"对准"挂在 `loop_ctrl_pending` 上，
而 `cmd_ready = !loop_ctrl_pending && …` 归零 —— **整条 UART 连读都不回**，直到 34 秒超时丢弃这次提交。

**修**（只动主机侧）：

| 文件 | 改动 |
| --- | --- |
| `session/record_flow.py` | `probe(page)`/`commit_pending()`；`arm()` 前先查 `0xF8` page 1 bit6/bit9，pending 就拒绝并提示"先发布" |
| `views/shell.py` | `commit_take()` 提交后**立刻 publish**（PLAY 提供边界）；`publish_take()` 容忍已 swap；`poll_board()` 把状态/BPM/身份/读数**整体挪到工作线程**，Tk 线程零 I/O |
| `link.py` / `session/core.py` | `command(attempts=)` / `read(attempts=)`：轮询用 1 次尝试（死链 0.4 s，不是 1.2 s） |
| `views/shell.py` | `io_busy()` 闸门：worker 在跑时完全不轮询；轮询 0.5 s → 1 s，BPM/身份 3 s 一次；`wait_for_take` 20 ms → 100 ms |

**实测**：重开控制台后空转 5.7 条命令/秒（原来 14），且全部在 worker 线程；237 条测试全绿
（新增 1 条：commit pending 时 arm 必须拒绝）。

**待办（要动板子）**：把 `BOUNDARY_TIMEOUT_CYCLES` 降到 5e8（5 s），或让 IDLE/RECORD 下的 swap 立即完成。

## 录音反馈：看得见 + 听得见

**触发**：用户"你现在这个没有提示啊，我都不知道有没有开始录"。

**做法**（全部主机侧，模型只存状态，窗口负责画）：

- `ConsoleModel.record_state`：`idle / countdown / armed / captured / failed`，`record_started` +

- 控件行：`● 录音中 轨 N x/32 tick`（原来那行只有一行灰字提示，几乎看不见）。
- 声音：倒计时每声 660 Hz、开窗 990 Hz、采下 1320 Hz，`winsound.Beep` 都在守护线程里。
