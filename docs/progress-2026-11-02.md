## 台架（2026-11-02 晚，板子在 IDLE，`0xB0=0x5A5A0003`）

### 1. 写路径节拍：**突发不可用**，保持逐条

`scripts/gui_burst_bench.py` 三档节拍全部 0 接受。深挖后是两个独立问题：

- **seq 是 8 位**：1024 条的突发里 seq 每 256 条回绕，按 seq 配对必然崩。→ `burst` 现在拒绝 >255 条。
- **板子会丢命令**：60/200/1000/2000 µs 间隔都只回约 36/64（56%），裸 pyserial 复现同样结果，
  所以不是适配层；也不再复现 2026-11-01 那次"400/400 全收"（那次是读 `0xB0`，板子状态不同）。

**决定**：突发关闭，上传与读回逐条等 ACK。实测（每次命令 17.2–17.6 ms）：

| 操作 | 命令数 | 墙钟 |
| --- | --- | --- |
| 九参数预设应用（写 + 读回） | 18 | ≈0.3 s |
| 1024 点上传 | 1029 | **18.1 s** |
| 1024 点逐点读回 | 2048 | **35.3 s** |

### 2. 台架抓出两个真 bug（都已修、都有测试）

- **`SerialPort.read` 每次改 `port.timeout`** → pyserial 的 setter 会重配端口，Windows 下
  **清掉驱动缓冲区** → 应答帧头被吃掉（实测收到 18/21 字节的残帧）。改成开端口时设一次
  timeout=0，读时轮询 `in_waiting`。
- **`read_table` 连读 1024 次拿到的是同一个点**：`WT_DATA` 读**不自增**索引（只有写入自增，
  `mgc3130_v2_top.sv:1478`），`board_readback.ps1` 是每点先写 `0x64`。改后实测 **1024/1024 全等**。

### 3. 板上验收（6 项里完成 3 项）

| # | 项目 | 结果 |
| --- | --- | --- |
| 1 | 身份 `0xB0` | ✅ `0x5A5A0003`，`STATUS=0x00000300`（IDLE，loop_active=1） |
| 2 | 应用 `warm` 九条与 `board_tune.ps1` 逐字一致 | ✅ 九条读回全等，`clamped` 为空 |
| 3 | 上传正弦表 + 读回 | ✅ `crc=0xAA59`、version 1→3、**1024/1024 全等** |
| 4 | 录一轨 → 提交 → 发布 | ✅ 覆盖 **32/32**，提交 **4 个事件**，`state=rolled`，mode 变 PLAY |
| 5 | `STOP` 后 `voices=0` | ✅ 播放中 3–5 个声部（`steals=0`、`overflow=0`），STOP 后 **0** |
| 6 | LIVE 页手在感应区有光标、离开时"等待光标" | ✅ 手在：**214 帧 / 2.5 s**（86 fps）、`0xE8=0x00000340`（note 64 / gate 1 / active 1）、`0xD4=386`；手离开：**0 帧**、`waiting()=True` |

**台架又抓到一个陷阱**：`0xE0` 是 `cursor_last_z`，光标从没有效过时它保持 **0**，而 `host-tools-and-gui-controls.md`
§9.3 的判据是"`raw_z < 30000` = 手在 engage 内"——会在"根本没光标"时误判成"手在按"。
`RecordFlow.diagnose()` 现在要求帧计数同时在涨（`engaged = alive and raw_z < 30000`），并有测试钉住。
